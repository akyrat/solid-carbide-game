**Hierarchy:** separate documents (source of truth) -> long GDD -> short GDD. Changes flow down only.

**One home for each fact:** each decision is written in exactly one document. Other documents point to it instead of repeating it.

## How the long and short GDD are made

- **Long GDD:** generated by a script from the game area docs (task T-007): exact, never rewritten by an agent, so it can't drift. Open questions and decision dates are left out. (Board decision, 2026-10-08.)
  - Regenerate it after changing a game area doc: `python tools/generate_long_gdd.py` (it writes nothing and exits 2 if a game area doc breaks the structure below, naming the file and line).
  - Staleness check, run at the start of each session and before milestones: `python tools/generate_long_gdd.py --check`. It changes nothing, lists every game area doc changed, added or removed since the long GDD was generated, and says whether the short GDD has caught up (exit 0 in sync, 1 stale, 2 structure problem).
- **Short GDD:** the pitch version, readable in one sitting. Written by the Project Lead from the long GDD in Markdown (`short-gdd/short-gdd.md`), with a PDF exported from it for sharing (task T-025). Visuals come later. (Board decision, 2026-10-08.)
  - Export the PDF after changing it: `python tools/export_short_gdd_pdf.py` (needs Microsoft Edge and an internet connection, for the Markdown and diagram libraries).
  - After bringing it up to date with the long GDD, update the "Last updated from long GDD" line in `short-gdd/README.md`, so the staleness check passes.

## The task board

The task board runs on this computer at <http://localhost:8765> (`tools/taskboard/server.py`, page `tools/taskboard/taskboard.html`). A hook starts it whenever a Claude Code session opens in this repo and shows its address; to start it by hand: `python tools/taskboard/server.py` (`--status`, `--stop`). Views: five lanes (To do, Planning, In progress, QA, Done) to drag tickets between, which the board can put in any order by dragging a lane's header (remembered in that browser; "Reset column order" puts back the default) and filter by label or status (Ready, Can start?, Waiting, Blocked, Planning, In progress, In QA, Playtest, Flagged, Done, Cancelled; several at once, also remembered), an Inbox (what needs the board, what is ready to start, what is waiting on what), and one bubble per game area doc showing how much of its work is done. Every ticket shows what it depends on and what it blocks. A Builds tab lists `master` and every worktree from `git worktree list` with its branch, ticket and the ticket's status. Each entry has a Play button (`"$GODOT_BIN" --path <folder>\game`) and an Open in editor button (`--editor`), which start Godot on this computer without a console window; both are disabled for a folder without `game/project.godot`, and a missing or wrong `GODOT_BIN` in `.env` shows an error on the page. A ticket that has a worktree shows a Play button and a link to its Builds entry in its detail view. The server only starts folders from its own worktree list (`GET /api/builds`, `POST /api/launch`).

The task files in `tasks/` are the board's only data. The server reads them, and the open task branches, every time the page checks (every 2 seconds), so the board is never behind and needs no sync.

- **Every status change goes through `python tools/task_status.py T-012 <status>`,** which checks the workflow rules (`tasks/README.md`, "Changing a task's status"). Hooks refuse direct edits to a task file's `status` and `qa_rounds` lines. The guard's rule for shell commands (board, 2026-10-20, T-212): it refuses only commands that can write a task file's `status`, `qa_rounds` or `lead` line, or that it can't read. Read-only and test commands pass even when they name task files and those words: `git status`, `git diff`, `git log`, the test runs (`python -m unittest`, `bash game/tools/run_tests.sh`), `grep` or `cat` of task files, inline code that names no task file, and scripts that only read. A script run from a file (`python x.py`, `bash x.sh`) is judged by its own code: it is refused when that code writes or matches a guarded header line, or names task files and writes files, or can't be found. Every refusal names the part of the command that caused it and why.
- **A drag on the board is a real move:** the server runs the same status script, so the task file changes straight away, or the card snaps back with the reason. Every drop onto another column opens a small box asking for an optional note (Enter moves, Shift+Enter adds a line, Esc cancels and the card stays); the note travels with the move to the ticket's owner session and is added to the ticket's result notes. Cancelling, or sending a playtest back, needs a note, typed in that box or in the ticket's details; if the server refuses, the box stays open with the note and the reason.
- **Out of QA with unmarked criteria** (board, 2026-10-20, T-212): dragging a ticket in QA to In progress or Planning while QA hasn't marked every acceptance criterion pass or fail opens a warning instead of the note box. It lists each unmarked criterion word for word (and any marked fail), with a box for the board's explanation of what has gone wrong, and Move anyway and Cancel buttons. Move anyway makes the move: the explanation is the move's note, added to the ticket's result notes and sent to its owner with the move; it is not a QA round. Cancel leaves the ticket as it was. The same warning opens for the move buttons in a ticket's details. The page asks `GET /api/move-check?id=T-012&status=in-progress` first; `POST /api/move` makes such a move only with `"confirm_unmarked": true`, and otherwise answers 409 with the warning and changes nothing. Other refused drags work as before.
- **The Project Lead hears about the board's moves** through hooks (`.claude/hooks/board_gate.py`): with the board's next message, when an agent comes back, and before it finishes a turn, and through its watcher (`python tools/board_inbox.py watch <session id>`). It then acts on them (starts the agent, runs QA, merges after a playtest).
- **Every session sees every drag that concerns it.** The server appends each drag to `.board/board-inbox.jsonl`, and nothing empties it. Each Project Lead session reads it with its own cursor, shared by its hooks and its watcher, so a move reaches a session once. A named session gets the moves on its own tickets, and those on tickets nobody owns with a note to claim them first; it never gets moves on another session's tickets. The one exception is a goal's ticket (lead `Goal-<goal id>`) once the run's headless session has ended (T-215): its moves then go to the session that started or resumed the run (the goal file's `session:` line), or, if that one isn't live, to one other live session, and the watcher's line says why (`tasks/README.md`, "Goal runs"). A session without a name gets every move, with a reminder to ask the board for a name. A new session starts at the end of the inbox and never replays older moves.
- **Owners:** each card shows its owner (the ticket's `lead`, `tasks/README.md`, "Owners") as a label, and nothing when it is unowned. A second row of filter buttons, "Owner", has one button per owner on any ticket plus "Unowned"; several can be picked, "Anyone" clears them, and the pick is remembered in that browser. A card shows when it matches the "Show" row and the "Owner" row. The Builds tab shows each worktree's owner next to its ticket. `/api/tickets` and `/api/builds` include `lead`.
- **The Project Lead's replies and the "New" highlight** (board, 2026-10-15, T-138): the reply the Project Lead gives the board at a lane change is also posted on the ticket (`task_status.py --reply`, `tasks/README.md`, "Changing a task's status"). The ticket's detail view shows it at the top in a "Latest from the Project Lead" box (date, lane change, text), with older replies folded in "Earlier updates (n)", newest first; a ticket without replies shows no box. `/api/tickets` includes each ticket's `updates`. A card in a lane gets a glowing cyan outline and a "New" chip when its status changed, or a reply was posted, since the board last opened that ticket; opening the ticket's detail view clears it, and the board's own drags count as seen. The Inbox's "Changed" list uses the same rule. What the board has seen is kept in that browser only.
- **Screenshots and recordings** (board, 2026-10-19, T-201): a ticket's media are the images and videos (`.png`, `.jpg`, `.gif`, `.webp`, `.mp4`, `.webm`) in `art-archive/<ticket id>/screenshots/` and its subfolders, plus any media file named on its `Board review files:` line (`tasks/README.md`, "Screenshots"). They are looked up where the ticket lives: its task folder while its branch is open, otherwise the main checkout. The ticket's detail view shows them in a "Screenshots and recordings" section (no section when there are none): images and GIFs as thumbnails, which open full size on a dark background with hard pixel edges (small pixel art is enlarged by a whole number; Esc or a click closes it), and MP4 and WebM as muted, looping video players with controls, each with its file name. A card shows a small count ("3 shots"). `/api/tickets` lists each ticket's `media` (relative `path`, `kind` image or video, `size`), and `GET /api/media?id=T-012&path=<relative path>` serves one of them, read-only, with its content type (byte ranges for scrubbing videos). It serves only files the ticket lists, and refuses `..`, absolute paths, other file types and anything outside the ticket's places. A new or changed screenshot refreshes the board like a changed task file.
- **Goals** (board, 2026-10-19, T-202): the goal runner's goals (`goals/G-NNN-*.md`, `tasks/README.md`, "Goal runs") are read from `goals/` in the main checkout, where the runner commits them, with the runner's own reader (`tools/goal_agent/goal_file.py`). A goal's tickets are the tickets whose `goal:` line names it, wherever the ticket lives (its task folder while its branch is open). A "Goals" strip above the lanes has one compact card per goal, newest first: its id, its title, a status chip (Planning, Planned, Building, Paused, Ready to play, Done, Cancelled; hovering a paused goal shows its latest pause reason), a progress bar with "N of M tickets done" (done and cancelled count as finished), "Art used of cap" when the cap is above 0, and its iteration. Done and cancelled goals are folded into a "Finished goals (n)" toggle, remembered in that browser. Clicking a goal card opens its detail: its status and progress, the goal's text, its tickets as links that open them (with a count per status), its pauses (newest first), a link that shows the goal file's full text, and, when its build folder (`C:\solid-carbide-worktrees\<goal id>`, from `git worktree list`) exists, the same Play and Open in editor buttons as that folder's Builds entry. A third row of filter buttons, "Goal", has one button per goal with tickets plus "No goal"; several can be picked, "Any" clears them, and the pick is remembered in that browser. A card shows when it matches all three rows. Each card in the lanes shows its goal's id as a small label, and the ticket's detail lists its goal. `GET /api/goals` returns each goal's header fields (`id`, `title`, `status`, `art_cap`, `art_used`, `iteration`, `max_iterations`, `created`, `lead`), `file`, `goal_text`, `pauses` and `latest_pause` (only while paused), `tickets` (ids), `ticket_counts` (per status), `tickets_total`, `tickets_finished`, `has_build` and `build_folder`; `GET /api/goal-file?id=G-004` returns one goal file's text, read-only. `/api/tickets` includes each ticket's `goal`. The page fetches the goals together with the tickets whenever the board's version changes (a changed goal file changes it too), and redraws the strip only when the goals' data changed.
- **What the agents are doing now** (board, 2026-10-19, T-203): the goal runner records every event of its headless sessions (agent, QA, goal check) in an activity log, `.board/activity/<ticket or goal id>.jsonl` in the main checkout (`tasks/README.md`, "Goal runs"), and the board turns the latest events into one plain phrase by fixed rules, not a model: "Reading `docs/level-design.md`", "Editing `ground_height.gd`", "Writing …", "Searching the files", "Running the game's tests" (`run_tests`), "Running the tools' tests" (unittest, pytest, `test_*.py`), "Taking screenshots", "Calling PixelLab", "Committing", "Using git", "Running the game", "Running a command", "Asking a helper agent", "Thinking", "Starting", "Finished"; QA's phrases start with "QA checking" and the goal check's with "Goal check"; any other tool is "Using <tool>". A run of the same phrase counts once. Every in-progress or in-QA card has a **Now line**: the phrase and how long it has been doing it ("Running the game's tests · 2 min"), or, for a ticket without an activity log (one a Project Lead session works on), its free signals: the commits on its own branch and its last activity ("3 commits · last activity 1 min ago"). The last activity is the newest of its activity log, its branch's last commit and its task file's change. A card with no activity for 10 minutes gets an orange dot and a "Quiet" chip. The ticket's detail view has a "Now" box at the top: the phrase, the time in its lane (from the moves log), the commits on its branch, the last activity, and the last 20 phrases with their times, newest first. A building goal's card shows the ticket being worked on, "ticket N of M, iteration K", and its phrase (or "Goal check" while the goal check runs). Each in-progress or in-QA ticket in `/api/tickets` has `now` (`phrase`, `phrase_since`, `phrase_age_s`, `step`, `timeline`, `in_lane_since`, `in_lane_s`, `commits`, `last_commit_at`, `file_changed_at`, `last_activity_at`, `last_activity_s`, `quiet`; the other tickets have `null`), and each building goal in `/api/goals` has `now` (`ticket`, `ticket_index`, `tickets_total`, `iteration`, `phrase`, `phrase_since`, `phrase_age_s`, `last_activity_at`, `quiet`). The Now lines follow the board's normal refresh: new events change the board's version at most once every 10 seconds, a new commit in a task folder changes it at once, and the page redraws the ages and quiet marks every 15 seconds. Only the end of each log is read (256 KB), a log past 2 MB keeps only its last 500 KB, and a log can be deleted at any time. To check the page with sample logs, start a second server on another port with `BOARD_PORT=<port>` and `BOARD_MAIN_STATE=<folder>` (a folder standing in for the main checkout's `.board/`, with `activity/` and `moves.log`).
- `.board/` (git-ignored) holds the moves log, the board's inbox for the Project Lead, each session's name and cursor (`.board/sessions/`), the server's log, and the goal runner's activity logs (`.board/activity/`).

## How separate documents are written

The nine separate documents (Extended narrative to HUD and menus in the table above; the board calls them game area docs) all follow one structure, so a script can build the long GDD from them (task T-007). The long GDD, short GDD, timeline and unfiled game details do not follow it.

```markdown
---
title: Drifting
gdd_order: 2
scope: One sentence on what this document covers.
agents_work_on: [driving-drift]
agents_read: []
---

# Drifting

## Summary

## Decisions

## Content

## Open questions

## References
```

**Header (front matter):** `title` is the chapter title in the long GDD. `gdd_order` is the chapter's position (1, 2, 3...). `scope` says what the document covers. `agents_work_on` and `agents_read` list agent names as in `.claude/agents/`. The Project Lead maintains every document.

**The five sections, always present, always in this order, and the only `##` headings allowed:**

- **Summary:** two to four sentences on what this part of the game is. It opens the document's chapter in the long GDD, and the short GDD condenses it.
- **Decisions:** one bullet per decision, ending with the date it was made, for example `(2026-10-04)`. Only decisions the board made. Ideas under consideration go in Open questions.
- **Content:** the full description, in prose, tables or diagrams. Use `###` subheadings freely. Content explains the decisions without repeating them.
- **Open questions:** what is still undecided. Open questions stay in this document and are not copied into the long GDD. A question that can wait until after the MVP starts with "(After MVP)"; the others must be answered for the MVP.
- **References:** links to research, reports and prototypes. The long GDD links to them; it does not copy them.

A section with nothing in it yet says `(To be written.)` or, for Open questions and References, `(None yet.)`.

**Writing rules:**

- Never write "see above" or "as mentioned earlier". Refer to another document by name and section, for example "Drifting, Decisions".
- Links are relative to the `docs/` folder, so they still work in the long GDD.
- Mermaid diagrams and relative image links are fine.
- One home for each fact: if a fact belongs in another document, link to it.
- The board's drawings and sketches are stored in a folder named after the game area doc they belong to (for example `docs/level-design/`), and linked from that doc's References.
