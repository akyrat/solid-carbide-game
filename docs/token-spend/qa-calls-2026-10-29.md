# Token spend: where a QA run spends its calls (2026-10-29)

The follow-up `docs/token-spend/after-2026-10-29.md` asked for: QA took about 33 calls per merged ticket in the HUD batch against 12.3 in the baseline, though T-347 meant to make QA cheaper. Written by T-358 on the board's go (2026-10-29). Analysis only: nothing here changes QA's definition, the guard or the scripts QA uses. The cuts at the end are proposals for the board.

## Read this first

- Tool: `python tools/qa_calls.py` (T-358). It reads only the `qa-integration` subagent transcripts, with the same layout, range rules and deduplication as `tools/token_report.py`, and groups each run's tool calls by kind. `--detail <agent id>` lists one run's tool calls in order, which is how the three dearest runs below were read (no transcript was read whole).
- Period: 2026-10-28T03:55:00Z to 2026-10-29T01:10:00Z (the HUD batch, as in `after-2026-10-29.md`). Baseline: everything up to 2026-10-28T01:43:02Z.
- A "call" is one model call (one message id), as in token_report. A "tool call" is one tool use; a call can carry several, so the period has 610 tool calls in 533 calls (about 0.87 calls per tool call). Savings below are given in tool calls and in calls at that ratio.
- Check against token_report for the same range: period 533 calls in both; baseline 3,656 in both. The baseline document says 3,507: that is token_report's own count when the baseline was taken; rerun today over the same range it gives 3,656, the same as this script, so the 149 difference (4%) comes from transcripts in the folder, not from this script.
- Two of the 20 period runs were not QA at all: they ran under the `qa-integration` agent type to merge HUD tickets into the playtest build (`a1575a33`, "Merge 4 HUD tickets to playtest", and `a02c1e9e`, "Merge HUD tickets to playtest"), 111 calls together. Without them: 18 QA runs, 422 calls, 23.4 per run, against 13.3 per run in the baseline.
- Runs that started before 03:55Z count only their calls after it (as token_report does).

## The three dearest runs, read by hand

1. `a1575a33`, 72 calls, "Merge 4 HUD tickets to playtest" (T-341, T-334, T-337, T-336, then resumed for T-351). Not a QA check: a playtest-build merge given to a `qa-integration` agent. Its calls went to merge conflicts in `hud.gd`, `hud.md` and the HUD tests between T-336 and T-337 (about 35 calls of git, `git show`, `awk` over conflict markers and python fixes), then the three test sets on the build branch run in the background and polled (19 polls, one sleep blocked), then a screenshot of the build. The second playtest merge, `a02c1e9e` (39 calls), is the same kind of work.
2. `acaa27b3`, T-355, 69 calls. The work check took about 15 calls. Then the Godot suite was started in the background and polled for the rest of the run: 42 poll calls in a fixed loop of Monitor `sleep 1750` (each timing out), `echo w`, and a `grep` of the log, many times over, before the suite reported. Then 5 refused or failed attempts to write the marks with a script before five Edits.
3. `a3e6e13f`, T-354, 43 calls. Reading the guard diff and probe scripts against the guard (about 15 calls, sensible for a guard ticket), the three test sets run by hand then polled (18 poll calls: Monitor `sleep 120/240/280`, `tail` of the output file, sleep blocked once), and 6 Edits of the ticket for the marks, after a refused python write.

The common thread: in every real QA run the dearest single part is waiting for the test sets. The three test sets take about 15 minutes in a row here (on T-358's branch: game/tools 87 s, tools 337 s, the Godot suite 472 s alone), longer than the 10-minute limit of one foreground command, and a foreground command was also seen moved to the background after 3 minutes while T-358's own tests ran. So `qa_check.py`, which runs all three in a row, cannot finish in one foreground call; QA starts it (or the sets) in the background and polls. QA's definition also runs `qa_check.py` a second time at the end without `--no-tests`, which reruns all three sets just to confirm the marks.

## Proposed cuts (proposals for the board; nothing changed)

Each with the calls it would have saved in the period (tool calls, then calls at 0.87 per tool call). They don't overlap.

| # | proposal | saved in the period |
|---|---|---|
| 1 | Waiting for the tests in one call. `qa_check.py` runs the three sets at the same time, or writes one result file that a single Monitor `until` call waits on, so a QA run spends at most one call waiting; and QA's last confirming run uses `--no-tests`, since the tests already ran. Per QA run: 2 `qa_check.py` calls and 1 wait instead of 13.3 calls on tests, qa_check and polling. | 240 - 54 = about 186 tool calls, about 160 calls |
| 2 | Marks in one command. A script command that writes all the criterion marks and the QA round note in one go (for example `qa_check.py T-NNN --mark 1=pass --mark 2="fail: code - ..."`), allowed by the guard, so QA stops trying `python -`, `sed -i` and `cat >>` (refused), then Edit before Read (refused), then one Edit per criterion. One call per QA run instead of 6.5. | 117 - 18 = 99 tool calls, about 86 calls |
| 3 | Playtest-build merges not on the QA agent. Either `merge_batch.py` learns to merge into a `playtest/<name>` branch, or these merges go to a general agent and are counted apart. This moves 111 calls out of QA's count; how many it saves depends on the conflicts (most of the 72-call run was resolving T-336 against T-337). | 111 calls out of QA's count; real saving unknown |
| 4 | Load Monitor before using it. 7 failed calls were Monitor called with ToolSearch's arguments before its schema was loaded, and 12 were `sleep` refused. Proposal 1 removes most of these; otherwise one line in QA's prompt. | covered by 1 (about 19 failed calls) |

With 1 and 2, the 18 QA runs would have taken about 422 - 160 - 86 = 176 calls, about 10 per run, under the baseline's 13.3. With 3 as well, QA calls per merged ticket would be about 176 / 16 = 11, against 33 in `after-2026-10-29.md`.
