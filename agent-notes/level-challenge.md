# Working copy: Level/Challenge Design Agent

This started as a copy of the original relationships in the agent's definition. Update it from experience so it reflects how this agent actually works. Over time it may shift from hand-offs toward naming the areas where agents overlap and how they interact. Changes to the original definition need the board's approval. This file does not.

These are guidelines for how work typically flows, not strict rules. Receiving work from an agent does not prevent sending work to it, and the other way around.

**Gets work from**

- Project Lead: Task files for the map and its challenges.
- Driving & Drift Agent: The verification script that checks a challenge design is achievable with the driving mechanics.
- Asset Generation Agent: Map and obstacle art.

**Hands work to**

- Enemy Behavior Agent: The map layout and where enemies can spawn.
- UI Agent: Challenge positions, for the arrow that points to the next one.
- QA/Integration Agent: The map and challenges to check.

**Collaborates with**

- Driving & Drift Agent: Challenges have to be drivable with the chosen drift, so they tune obstacle spacing and track width together.
- Enemy Behavior Agent: Where enemies spawn depends on the map layout, so each adjusts to the other.

## Notes from experience

- T-019 (MVP map): the map and its fitted patterns are generated by a script (`game/tools/build_mvp_map.py`) from the board's sketches, so a change of placement or challenge choice is an edit to its lists plus a rerun, not hand work.
- Overlap with Driving & Drift: the map only provides colliders and the completion check; the car's collision response (the slight bounce) and the drivability script (T-021) are theirs. Every challenge stays "needs the drivability check" until T-021 runs on it.
- Overlap with UI and Game Loop: the map's `challenge_completed(challenge_id)` signal and `get_challenge(id)` are the hand-off points for XP, the HUD and the next-challenge arrow.
- T-035 (meteor challenges): the challenge designs are stored unplaced in the layout data (`challenge_designs`), so runtime challenges place them with any angle. The hand-off to Enemy Behavior is `can_place_meteor_challenge`, `add_meteor_challenge` and the separate `meteor_challenge_completed` signal (documented in `game/README.md`); how many open at once and where meteors land are theirs.
- The build script's tests broke when T-021 added `.driven.json` files next to the sketches; generated files next to the sketches should always be skipped by name (anything with a second dot), not one suffix at a time.
- T-094 (map made bigger): copies and challenges are now made by rules in the build script (`make_copies()`, `make_challenges()`), not hand lists, so a size change is a few constants. Tests that hard-code map coordinates (the meteor placement tests, the screenshot fixture, the run's challenge count) are the ones to revisit when the map changes. Check a target size against the grid's arithmetic (18 N + 8 for 10-unit blocks and 8-unit roads) before building, and say so when the asked size cannot be made exactly.
- T-096 (everything three times bigger): the fitting contexts must follow the road width (they read `ROAD` now), not a hard-coded 8. With 24-unit roads the board's sketches fit as drawn, so the fitted versions became the sketches moved onto the pattern centre; a test now pins that, so a future squeeze shows up as a failing test rather than silently.
- T-097 (challenges out of the MVP): turned off with one switch (`CHALLENGES_ENABLED` in `mvp_map.gd`, passed through the run's `challenges_enabled`), keeping the data, code and their tests (which now switch challenges on in their `make_map()`). Tests and fixtures that picked `challenge_ids()[0]` to fake a completion now read the id from the layout data, so they don't depend on the switch. The hand-off to Enemy Behavior for the kaiju's meteors is now `can_place_meteor_boulder` and `add_meteor_boulder`.
- T-034 (see-through buildings): buildings are now one node each (`map_building.gd`) with a `z_index` depth order; the car's place in it goes on the run's `View` through `map.car_z_index()`. Overlap with Game Loop (run.gd's `sync_view`) and UI (trick popups at z 100 inside `View`, so buildings must stay under z 100). On the big 30-unit blocks a single x + y depth number is wrong for "behind" (a car just in front of a long wall has a smaller x + y than the front corner); use "not in front of either visible wall" instead.
