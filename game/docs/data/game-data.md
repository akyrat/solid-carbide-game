## Game data

Written by the Game Data Agent (task T-038); the enemy, weapon and garage data tasks follow the same convention.

- **Where:** one JSON file per area under `game/data/` (`run.json` for the run's XP, levels and car starting health). Keys are `snake_case`. A `_comment` key may explain a file. Numbers are proposals the board judges in playtests, and are changed in the file, never in code.
- **Loader:** `scripts/data/game_data.gd` (`GameData`). `GameData.load_file("run")` reads `res://data/run.json`; `GameData.get_value(data, "car.starting_health")` reads a dotted path (array indexes as numbers). Both return `{ok, data, error}`: a missing file, invalid JSON or missing value gives `ok = false` and a clear `error` message. `GameData.unwrap(result)` returns the data, or `push_error`s the message and returns null.
- **Typed readers:** for each data file, a small class next to the loader wraps it so game code does not index dictionaries. `scripts/data/run_data.gd` (`RunData`) gives `xp_needed(level)`, `challenge_xp(level)`, `drift_xp_per_second()`, `max_level()`, `carries_over()`, `starting_health()`, and the likes drain (`likes_drain` in `run.json`, task T-114): `likes_drain_enabled()`, `likes_drain_bar_share_per_second()` (share of the current level's bar drained per second, 0.08, the board's playtest value since T-120: a full bar empties in 12.5 s, 8 likes a second at level 1), `likes_drain_extra_wait_seconds()` (wait after the combo has fully drained, 0) and `likes_drain_xp_per_second(level)` (the share times that level's `xp_needed`, 0 when off or at max level). `scripts/data/combo_data.gd` (`ComboData`, from `combo.json`) gives `trick_add(trick)`, `after_trick()`, `after_collision()`, `after_idle()` and `spawn_multiplier()`.
- **Garage:** `garage.json` holds the 5 upgrades (`acceleration`, `car_health`, `damage_bonus`, `pickup_magnet`, `air_turn`), 10 levels each, with a `price` and a `value` per level and a `base_value` for level 0. `scripts/data/garage_data.gd` (`GarageData`) gives `max_level()`, `price(upgrade, level)` and `value(upgrade, level)`. Tests: `tests/unit/test_garage_data.gd`. **Air turn upgrade (T-270, "Spin Doctor", key `air_turn`):** the value is the air turn's total multiplier of the ground rate (base 1.25 at level 0, +0.125 per level, 2.5 at level 10; prices 40 to 300 as the acceleration upgrade). `GameFlow.start_run()` calls `run.car.tuning.apply_air_turn_upgrade(progress)`, which passes the bought value minus 1.25 to `apply_air_turn_bonus()` (T-269's hook); the drift prototype never calls it. An air 360 off the tallest rooftop is reachable from level 6 (2.0). Tests: `tests/unit/game/test_air_turn_upgrade.gd`, plus `test_garage_data.gd` and `test_garage_screen.gd`. Screenshot: `art-archive/T-270/screenshots/garage_air_turn.png`.
- **Weapons (T-040):** `data/weapons.json` holds the starting gun, the exhaust flamethrower and (T-166, proposals for the board's playtest) the neon underglow (`underglow`), the molotovs (`molotov`) and the windshield wiper (`wiper`, the only entry with a knockback strength): base values and, for each, the 7 upgrade tiers (tiers 2 to 8) as `effect` plus `value`. `scripts/data/weapon_data.gd` (`WeaponData`) adds the tiers up: `gun_at(tier)`, `flame_at(tier)`, `underglow_at(tier)`, `molotov_at(tier)` and `wiper_at(tier)` return the weapon's values at that tier (tier 1 = just got it), and `tiers(weapon)` the raw list. **Bricks (T-323, numbers only):** `bricks` has `damage`, `radius`, `knockback_distance`, `min_air_seconds`, `cooldown` and 7 tiers, read through `bricks_at(tier)`; `offered_in_level_ups` (false, `bricks_offered()`) keeps it out of the level-up offers until T-324 builds the weapon: T-324 sets it true and adds `bricks` to `WEAPON_ORDER` and `get_bricks` / `upgrade_bricks` to `ALL_IDS` in `scripts/weapons/level_up_offers.gd` (and updates the tests that list the five weapons). Tests: `tests/unit/test_weapon_data.gd`, which compares everything with the Unity weapons report.
- **Enemies (T-039):** `data/enemies.json` holds the minion (`health`, `move_speed`, `contact_damage`, `contact_damage_interval`, `knockback`), `spawning` (how many minions are kept around: `minions_at_start`, growing in a straight line to `minions_at_boss_time` at `growth_until_seconds` = the kaiju's arrival, then held; one spawns every `spawn_interval_seconds` while fewer are around, `spawn_margin_units` beyond the visible screen's edge), `coins` (`drop_chance`, `coins_per_drop`), the `kaiju` (same keys as the minion), `kaiju_coins` (T-119: the coins the kaiju drops when defeated, `drop_chance` 1 = always and `coins_per_drop`; its death ends the run, so they are added to the run's coins as it ends, without a pickup) and its `meteor_attack` (`first_attack_after_seconds`, `seconds_between_attacks`, `windup_seconds`, `meteors_per_attack`, `warning_seconds` (decided, 2 s), `land_within_units_of_car`, `impact_radius_units`, `impact_damage`, `knockback`, `boulder_lifetime_seconds`, `boulder_fade_seconds`, `boulder_clearance_units`). Units as everywhere: 1 unit = the car's width, speeds and knockback in units per second, damage in the car's health points. `scripts/data/enemy_data.gd` (`EnemyData`) gives each section as a Dictionary of floats (`minion()`, `spawning()`, `coins()`, `kaiju()`, `meteor_attack()`), `kaiju_coins()`, `minions_wanted(run_seconds, spawn_multiplier = 1.0)` (pass `ComboData.spawn_multiplier(combo)` for the combo's extra spawning), `expected_coins_per_kill()`, `kaiju_coins_on_defeat()` (whole coins the defeated kaiju adds) and `meteor_attack_times(fight_seconds)`. Enemy stats never change over a run; only `minions_wanted` grows. Tests: `tests/unit/test_enemy_data.gd`, including the kaiju's time to kill with the MVP weapons and its coins when defeated.
- **Playtest switches:** `data/playtest.json` holds switches for playtests only, not balancing numbers and never shown to the player: a dictionary of independent keys, each read by its own task's code. `flamethrower_at_start` (T-042, see "Weapons") and `kaiju_early_arrival` (T-045, see "The kaiju"). Each reading script has a static `playtest_override` that tests set, so the tests follow the game's rules whatever the file says.
- **Saving and buying (T-057):** `scripts/data/player_progress.gd` (`PlayerProgress`) keeps the player's coins and the garage upgrade levels in `user://progress.json` (`{"coins": n, "levels": {"acceleration": 0, ...}}`). A missing or broken file is a new player: 0 coins, every level 0. `GameFlow.progress` is the game's instance; it banks each run's coins on `run_ended` (win or loss) and saves. Tests set the static `PlayerProgress.path` to `RunPaths.file(...)`. Functions, for the garage screen (T-058) and for applying upgrades at the start of a run (T-060, T-061, T-062); upgrade ids are `GarageData.UPGRADES`:
  - `get_coins() -> int` and the `coins` field; `level(id) -> int`; `is_maxed(id) -> bool`.
  - `next_price(id) -> int` (coins for the next level, -1 when maxed).
  - `current_value(id) -> float` (the stat at the current level: time to top speed in seconds, starting health, damage bonus in percent; level 0 is the base) and `next_value(id) -> float` (-1.0 when maxed). Apply an upgrade at run start by reading `current_value(id)`.
  - `info(id) -> Dictionary` with `id`, `level`, `max_level`, `maxed`, `next_price`, `current_value`, `next_value`, `can_buy`, everything a garage row shows.
  - `can_buy(id) -> String`: `PlayerProgress.OK` (empty), or the refusal reason `NOT_ENOUGH_COINS`, `MAXED` or `UNKNOWN_UPGRADE`.
  - `buy(id) -> Dictionary` `{"ok": bool, "reason": String}`: if it can be bought it spends the price, raises the level and saves; a refusal changes nothing.
  - `bank_run(result, coins)` adds a run's coins and saves; `connect_run(run_state)` connects it to `run_ended`. `changed` is emitted after buying or banking. `save()` and `load_from_disk()` are there for completeness.
  - Tests: `tests/unit/test_player_progress.gd`.
- **Upgrades reach the car (T-060):** `GameFlow.start_run()` calls `run.car.tuning.apply_acceleration_upgrade(progress)` (`scripts/driving/car_tuning.gd`) right after the run is built, which sets the car's `time_to_top_speed` to `progress.current_value("acceleration")` (level 0 is the base, 2.3 s, the car's default, so the car drives exactly as before). Only runs started through `GameFlow` get it; the drift prototype never calls it and keeps its own tuning and sliders. Because W snaps to cruise speed first, the real climb to top speed is a fixed share of that time, so it scales with the data. Health and damage upgrades (T-061, T-062) are applied the same way at run start. Tests: `tests/unit/game/test_acceleration_upgrade.gd`.
  - **Damage bonus (T-062):** `GameFlow.start_run()` calls `run.weapons.set_damage_bonus(progress.current_value("damage_bonus"))` right after the run is added. The rack keeps `damage_bonus_percent`; `damage_multiplier()` is `1 + percent / 100`. Each weapon's `apply_tier()` multiplies that tier's damage with `boosted_damage()` (weapon.gd), so the gun's bullets and the flame's ticks get the same factor, it stacks multiplicatively with the tier's own damage (the flame's hotter-flame tier), and it survives a new run's weapon reset. Level 0 is 0 percent: unchanged. Tests: `tests/unit/weapons/test_damage_bonus.gd`.
- **Gift pack (T-144):** `data/gift_pack.json` holds the gift pack drop's numbers (`helicopter`: `speed_px_per_second`, `drop_height_px`, `offscreen_margin_px`; `package`: `fall_seconds`, `land_ahead_units`, `clearance_units`, `pickup_radius_units`). `scripts/data/gift_pack_data.gd` (`GiftPackData`) gives one function per key. See "The gift pack drop". Tests: `tests/unit/run/test_gift_drops.gd`.
- **Tests:** `tests/unit/test_run_data.gd`, `tests/unit/test_combo_data.gd`, `tests/unit/test_garage_data.gd`, `tests/unit/test_weapon_data.gd`, `tests/unit/test_enemy_data.gd`. New data files get a test that loads them through the loader.
