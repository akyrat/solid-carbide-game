# Game data

## Game data

Written by the Game Data Agent (task T-038); the enemy, weapon and garage data tasks follow the same convention.

- **Where:** one JSON file per area under `game/data/` (`run.json` for the run's XP, levels and car starting hearts, invulnerability and blink). Keys are `snake_case`. A `_comment` key may explain a file. Numbers are proposals the board judges in playtests, and are changed in the file, never in code.
- **Loader:** `scripts/data/game_data.gd` (`GameData`). `GameData.load_file("run")` reads `res://data/run.json`; `GameData.get_value(data, "car.starting_hearts")` reads a dotted path (array indexes as numbers). Both return `{ok, data, error}`: a missing file, invalid JSON or missing value gives `ok = false` and a clear `error` message. `GameData.unwrap(result)` returns the data, or `push_error`s the message and returns null.
- **Typed readers:** for each data file, a small class next to the loader wraps it so game code does not index dictionaries. `scripts/data/run_data.gd` (`RunData`) gives `xp_needed(level)`, `challenge_xp(level)`, `drift_xp_per_second()`, `max_level()`, `carries_over()`, `starting_hearts()` (5; `starting_health()` still returns the same number until T-334 renames the run's health), `invulnerability_seconds()` (1.0), `blink_interval_seconds()` (0.1) and the likes drain (`likes_drain` in `run.json`, task T-114): `likes_drain_enabled()`, `likes_drain_bar_share_per_second()` (share of the current level's bar drained per second, 0.08, the board's playtest value since T-120: a full bar empties in 12.5 s, 8 likes a second at level 1), `likes_drain_extra_wait_seconds()` (wait after the combo has fully drained, 0) and `likes_drain_xp_per_second(level)` (the share times that level's `xp_needed`, 0 when off or at max level). `scripts/data/combo_data.gd` (`ComboData`, from `combo.json`) gives `trick_add(trick)`, `after_trick()`, `after_collision()`, `after_idle()` and `spawn_multiplier()`.
- **Garage:** `garage.json` holds the 5 upgrades (`acceleration`, `car_health`, `damage_bonus`, `pickup_magnet`, `air_turn`), 10 levels each, with a `price` and a `value` per level and a `base_value` for level 0 (T-415: `car_health` and `pickup_magnet` store a `bonus` per level instead and no base: the base is `run.json`'s `car.starting_hearts` and `pickup_magnet.radius_units`, `GarageData.value()` adds them, `bonus()` gives the part the garage adds). `scripts/data/garage_data.gd` (`GarageData`) gives `max_level()`, `price(upgrade, level)` and `value(upgrade, level)`. Tests: `tests/unit/test_garage_data.gd`. **Air turn upgrade (T-270, "Spin Doctor", key `air_turn`):** the value is the air turn's total multiplier of the ground rate (base 1.25 at level 0, +0.125 per level, 2.5 at level 10; prices 40 to 300 as the acceleration upgrade). `GameFlow.start_run()` calls `run.car.tuning.apply_air_turn_upgrade(progress)`, which passes the bought value minus 1.25 to `apply_air_turn_bonus()` (T-269's hook); the drift prototype never calls it. An air 360 off the tallest rooftop is reachable from level 6 (2.0). Tests: `tests/unit/game/test_air_turn_upgrade.gd`, plus `test_garage_data.gd` and `test_garage_screen.gd`. Screenshot: `art-archive/T-270/screenshots/garage_air_turn.png`.
- **Weapons (T-040):** `data/weapons.json` holds the starting gun, the exhaust flamethrower and (T-166, proposals for the board's playtest) the neon underglow (`underglow`), the molotovs (`molotov`) and the windshield wiper (`wiper`, the only entry with a knockback strength): base values and, for each, the upgrade tiers (tiers 2 to 8; Bricks and the wiper to tier 7 for now, each with its own `max_tier`; T-496, the board's own trees) as `effect` plus `value`. `scripts/data/weapon_data.gd` (`WeaponData`) adds the tiers up: `gun_at(tier)`, `flame_at(tier)`, `underglow_at(tier)`, `molotov_at(tier)` and `wiper_at(tier)` return the weapon's values at that tier (tier 1 = just got it), and `tiers(weapon)` the raw list. **Bricks (T-323, numbers only):** `bricks` has `damage`, `radius`, `knockback_distance`, `min_air_seconds`, `cooldown` and 7 tiers, read through `bricks_at(tier)`; `offered_in_level_ups` (false, `bricks_offered()`) keeps it out of the level-up offers until T-324 builds the weapon: T-324 sets it true and adds `bricks` to `WEAPON_ORDER` and `get_bricks` / `upgrade_bricks` to `ALL_IDS` in `scripts/weapons/level_up_offers.gd` (and updates the tests that list the five weapons). Tests: `tests/unit/test_weapon_data.gd`, which compares everything with the Unity weapons report.
- **Missions and driving power-ups (T-455, proposals):** `data/missions.json` holds `total` (30), `known_tricks`, the 5 `fixed` missions and the `generator` rules (goals per mission by range, and per trick a `base`, `growth_per_mission` and `max`, each with a `reason` and `proposal: true`). `scripts/data/mission_data.gd` (`MissionData`): `total()`, `fixed()`, `trick_rules()`, `goals_for(n)`, `amount_for(rule, n)`, `mission(n, rng)`. `data/power_ups.json` holds the four power-ups (`rev_charge`, `jump`, `bouncy_bumpers`, `rusty_overcoat`) with an `icon` path and 4 `tiers` each, plus `offer_when_exhausted` (`skip_gift`). `scripts/data/power_up_data.gd` (`PowerUpData`): `ids()`, `icon(id)`, `tiers(id)`, `at(id, tier)`, `max_tier(id)`, `offer_when_exhausted()`. Tests: `tests/unit/test_mission_data.gd`.
- **Enemies (T-039):** `data/enemies.json` holds the minion (`health`, `move_speed`, `contact_damage` in hearts (1), `knockback`; the 0.5 s `contact_damage_interval` is gone, T-333), `spawning` (how many minions are kept around: `minions_at_start`, growing in a straight line to `minions_at_boss_time` at `growth_until_seconds` = the kaiju's arrival, then held; one spawns every `spawn_interval_seconds` while fewer are around, `spawn_margin_units` beyond the visible screen's edge), `coins` (`drop_chance`, `coins_per_drop`), the `kaiju` (same keys as the minion), `kaiju_coins` (T-119: the coins the kaiju drops when defeated, `drop_chance` 1 = always and `coins_per_drop`; its death ends the run, so they are added to the run's coins as it ends, without a pickup) and its `meteor_attack` (`first_attack_after_seconds`, `seconds_between_attacks`, `windup_seconds`, `meteors_per_attack`, `warning_seconds` (decided, 2 s), `land_within_units_of_car`, `impact_radius_units`, `impact_damage`, `knockback`, `boulder_lifetime_seconds`, `boulder_fade_seconds`, `boulder_clearance_units`). Units as everywhere: 1 unit = the car's width, speeds and knockback in units per second, damage in the car's health points. `scripts/data/enemy_data.gd` (`EnemyData`) gives each section as a Dictionary of floats (`minion()`, `spawning()`, `coins()`, `kaiju()`, `meteor_attack()`), `kaiju_coins()`, `minions_wanted(run_seconds, spawn_multiplier = 1.0)` (pass `ComboData.spawn_multiplier(combo)` for the combo's extra spawning), `expected_coins_per_kill()`, `kaiju_coins_on_defeat()` (whole coins the defeated kaiju adds) and `meteor_attack_times(fight_seconds)`. Enemy stats never change over a run; only `minions_wanted` grows. Tests: `tests/unit/test_enemy_data.gd`, including the kaiju's time to kill with the MVP weapons and its coins when defeated.
- **Playtest switches:** `data/playtest.json` holds switches for playtests only, not balancing numbers and never shown to the player: a dictionary of independent keys, each read by its own task's code. `flamethrower_at_start` (T-042, see "Weapons") and `kaiju_early_arrival` (T-045, see "The kaiju"). Each reading script has a static `playtest_override` that tests set, so the tests follow the game's rules whatever the file says.
- **Saving and buying (T-057):** `scripts/data/player_progress.gd` (`PlayerProgress`) keeps the player's coins and the garage upgrade levels in `user://progress.json` (`{"coins": n, "levels": {"acceleration": 0, ...}}`). A missing file is a new player: 0 coins, every level 0. Saves are safe (T-417, `scripts/data/safe_save.gd`, `SafeSave`): a save writes `progress.json.tmp` and renames it over the file, after copying the last good file to `progress.json.bak`; every save holds `"version"` (1; a file without one loads as version 1, `loaded_version`); a file that fails to load is renamed aside to `progress.json.broken-<unix time>`, never overwritten, and the backup loads in its place (`loaded_from` is `main`, `backup` or `none`). Renamed upgrade ids: `PlayerProgress.ID_RENAMES` (save version -> {old id: new id}), empty today; when an upgrade is renamed, raise `SafeSave.CURRENT_VERSION` and add the mapping. `RunHistory` follows the same rules. Tests: `tests/unit/test_safe_save.gd`. `GameFlow.progress` is the game's instance; it banks each run's coins on `run_ended` (win or loss) and saves. Tests set the static `PlayerProgress.path` to `RunPaths.file(...)`. Functions, for the garage screen (T-058) and for applying upgrades at the start of a run (T-060, T-061, T-062); upgrade ids are `GarageData.UPGRADES`:
  - `get_coins() -> int` and the `coins` field; `level(id) -> int`; `is_maxed(id) -> bool`.
  - `next_price(id) -> int` (coins for the next level, -1 when maxed).
  - `current_value(id) -> float` (the stat at the current level: time to top speed in seconds, starting health, damage bonus in percent; level 0 is the base) and `next_value(id) -> float` (-1.0 when maxed). Apply an upgrade at run start by reading `current_value(id)`.
  - `info(id) -> Dictionary` with `id`, `level`, `max_level`, `maxed`, `next_price`, `current_value`, `next_value`, `can_buy`, everything a garage row shows.
  - `can_buy(id) -> String`: `PlayerProgress.OK` (empty), or the refusal reason `NOT_ENOUGH_COINS`, `MAXED` or `UNKNOWN_UPGRADE`.
  - `buy(id) -> Dictionary` `{"ok": bool, "reason": String}`: if it can be bought it spends the price, raises the level and saves; a refusal changes nothing.
  - `bank_run(result, coins)` adds a run's coins and saves; `connect_run(run_state)` connects it to `run_ended`. `changed` is emitted after buying or banking. `save()` and `load_from_disk()` are there for completeness.
  - Tests: `tests/unit/test_player_progress.gd`.
- **Cosmetics (T-552):** `data/cosmetics.json` (the 5 jump effects and prices), `scripts/data/cosmetics_data.gd` (`CosmeticsData`), and the saved choice in `PlayerProgress` (`cosmetics_list()`, `is_unlocked(id)`, `can_afford(id)`, `buy_cosmetic(id)`, `equip(id)`, `equipped_jump_effect()`); details in Garage design, "Cosmetics data". Tests: `tests/unit/test_cosmetics.gd`.
- **Run history (T-363):** `scripts/data/run_history.gd` (`RunHistory`) keeps every finished run in `user://run_history.json` (`{"runs": [entry, ...]}`, oldest first in the file). An entry is `RunState.recap()` (`result` "win" or "loss", `loss_reason` "time" or "health" or "", `time_survived`, `coins`, `likes`, `level`, `enemies_slain`, `tricks`, `highest_combo`, `peak_viewers` (since T-320), `weapons`) plus `ended_at` (local "YYYY-MM-DDTHH:MM:SS") and `ended_unix`. Cap: `MAX_RUNS` = 200, the oldest dropped (a proposal). A missing file is an empty history; a broken one is kept aside and the backup loads, with a version like the progress save (T-417). `runs()` returns copies, newest first (for the runs list, T-364); `count()`; `add_run(recap, ended_unix = now)` (ignores a recap with no result) saves and emits `changed`; `connect_run(run_state)` saves the final recap on `run_ended`, once. `GameFlow.history` is the game's instance, passed to `add_run(...)` so each game run is saved; the level creator's Play is not. Tests set the static `RunHistory.path` to `RunPaths.file(...)` (`TestSave` does it for the whole run). Tests: `tests/unit/test_run_history.gd`.
- **Upgrades reach the car (T-060):** `GameFlow.start_run()` calls `run.car.tuning.apply_acceleration_upgrade(progress)` (`scripts/driving/car_tuning.gd`) right after the run is built, which sets the car's `time_to_top_speed` to `progress.current_value("acceleration")` (level 0 is the base, 2.3 s, the car's default, so the car drives exactly as before). Only runs started through `GameFlow` get it; the drift prototype never calls it and keeps its own tuning and sliders. Because W snaps to cruise speed first, the real climb to top speed is a fixed share of that time, so it scales with the data. Health and damage upgrades (T-061, T-062) are applied the same way at run start. Tests: `tests/unit/game/test_acceleration_upgrade.gd`.
  - **Damage bonus (T-062):** `GameFlow.start_run()` calls `run.weapons.set_damage_bonus(progress.current_value("damage_bonus"))` right after the run is added. The rack keeps `damage_bonus_percent`; `damage_multiplier()` is `1 + percent / 100`. Each weapon's `apply_tier()` multiplies that tier's damage with `boosted_damage()` (weapon.gd), so the gun's bullets and the flame's ticks get the same factor, it stacks multiplicatively with the tier's own damage (the flame's hotter-flame tier), and it survives a new run's weapon reset. Level 0 is 0 percent: unchanged. Tests: `tests/unit/weapons/test_damage_bonus.gd`.
- **Gift pack (T-144):** `data/gift_pack.json` holds the gift pack drop's numbers (`helicopter`: `speed_px_per_second`, `drop_height_px`, `offscreen_margin_px`; `package`: `fall_seconds`, `land_ahead_units`, `clearance_units`, `pickup_radius_units`). `scripts/data/gift_pack_data.gd` (`GiftPackData`) gives one function per key. See "The gift pack drop". Tests: `tests/unit/run/test_gift_drops.gd`.
- **Live viewers (T-332), removed in T-514:** `data/viewers.json` and `scripts/data/viewers_data.gd` are gone; the combo shows as its multiplier (`MultiplierTag`, `docs/hud-and-menus/hud.md`).
- **Tests:** `tests/unit/test_run_data.gd`, `tests/unit/test_combo_data.gd`, `tests/unit/test_garage_data.gd`, `tests/unit/test_weapon_data.gd`, `tests/unit/test_enemy_data.gd`. New data files get a test that loads them through the loader.
